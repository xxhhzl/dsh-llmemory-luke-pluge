# dsh-longmemory 项目全景：这个插件是怎么记住你的

> 面向人读者的通俗版。读完你会知道：你聊完一段话之后，它经历了什么、被存成了什么样、下次又是怎么被想起来的。

---

## 一、一句话说明白

这是一个给 DeepSeek Harness（DSH）用的**长期记忆插件**。你和大模型的对话会随会话结束而消失，这个插件把对话**切成一段段「事件」**，再从事件里**提炼出经验、认知、洞见**存进本地 SQLite 数据库；下次你提到「之前」「上次」「我们讨论过」时，模型能通过工具把这些记忆**搜回来接着用**。

它仿照的是人类记忆的分层：

| 层级 | 名字 | 类比 | 例子 |
|---|---|---|---|
| L1 | message（原文） | 你记得的每句话 | 「把边框改成 1px」 |
| L2 | event（事件） | 一件完整的事 | 「改 SVG 边框并导出」+ 200 字摘要 |
| L3 | experience / cognition | 教训和事实 | 「编辑前先读当前内容」/「用户偏好中文」 |
| L4 | insight（洞见） | 多条教训归纳出的规律 | 「凡是批量改文件，都该先逐个确认现状」 |
| 另存 | self_memory | 自我认知 | 「我是擅长逆向的助手」 |
| 缓存 | digest（工作记忆） | 桌面上的便签 | 最近 5 件事 + 最重要的几条经验 |

## 二、两块拼起来的系统：JS 外壳 + Python 内核

```
┌─ DSH 宿主（DeepSeek Harness）────────────────────────┐
│                                                        │
│   JS 外壳（src/js/，一个 Cordis 插件）                  │
│   ├── kernel.js     负责启动/监控 Python 子进程         │
│   ├── ingest-bridge.js  监听会话事件，攒一批发给内核     │
│   ├── llm-bridge.js   把内核的「帮我调模型」请求转给宿主  │
│   ├── tools-bridge.js 把内核的工具注册给宿主            │
│   ├── core-prompt.js  把核心记忆注入系统提示词          │
│   └── shell.js      把上面这些装配起来                 │
│                    │ stdin/stdout 一行一条 JSON         │
│   Python 内核（src/*.py，一个子进程）                   │
│   ├── main.py       读帧、分发、回帧                   │
│   ├── segmenter.py  把对话切成事件                     │
│   ├── summary.py    调模型写摘要+提炼经验/认知（调用A）  │
│   ├── consolidate.py 判新旧记忆该不该合并（调用B）       │
│   ├── ingest.py     落库流水线 + 后台 worker            │
│   ├── database.py   SQLite 存储                       │
│   ├── retrieval.py  检索排序                          │
│   ├── insight.py    离线归纳洞见                       │
│   └── tools.py      给模型用的 5 个工具                 │
└────────────────────────────────────────────────────────┘
```

**为什么分两个进程？** 模型调用的 API key 在宿主手里，内核拿不到也不该拿到。所以内核每次想调模型，就往外发一条 `llm.request` 帧，外壳替它调完再回一条 `llm.result`。embedding 同理（`embed.request`/`embed.result`）。内核因此可以在任何机器上离线测试——测试里把「调模型」换成假的即可。

**为什么用 SQLite？** 单文件、零依赖、WAL 模式下读不挡写，记忆库跟着项目文件夹走，拷贝即备份。

## 三、写入链路：你的一段话怎么变成记忆

这是插件最核心的一条流水线。你每聊几句，外壳就把新消息打包发给内核，内核在后台线程里做四件事：

```
你说话 → ① 存原文 → ② 切事件 → ③ 写摘要+提炼 → ④ 合并判重 → 落库
```

### ① 存原文（ingest.py `_store_messages`）

- 每条消息带 `msg_id`、`seq`（序号）、`role`、`content`，整批在一个事务里写入 `message` 表。
- 入库前过一遍**脱敏**（sanitize.py）：`sk-xxx`、Bearer token、`password=...` 这类凭据会被替换成 `[REDACTED]`——记忆库比配置文件更容易被整库拷走。
- `msg_id` 重复就跳过（幂等），`seq` 撞车（不同消息抢同一序号）单独计数告警。
- 时间统一换算成 UTC 字符串，免得「+08:00」和「Z」混存后按字符串排序整体错位 8 小时。

### ② 切事件（segmenter.py + jev.py）

把消息流切成「一段一段完整的事」。切分是**规则优先、模型兜底**的分层判定：

1. **G0 硬规则**（不花模型钱，先看明显的）：
   - 事件正文超过 token 预算（默认 128K）→ 切；
   - 用户说了「换个话题」「新任务」等转折词 → 切；
   - 助手紧接着回答用户 → 不切（同一件事）；
   - 时间间隔超过 2 小时 → **不直接切**（隔夜继续同一件事很常见），标记为「软先验」交给模型判。
2. **G1 快判**：拿「当前事件摘要是啥 + 上一条 + 这一条」问一次便宜模型：这是新事件吗？模型给出 CONTINUE/SPLIT 和置信度。
3. **G2 深思**（可选）：置信度落在 0.4–0.6 的灰带，换个更强的模型再问一次。
4. **G3 兜底**：还不确定 → 不切，但打上 `needs_review` 标记。

**增量切分**：每次只处理「最后一条已归属事件的消息之后」的新消息。旧实现每次把整个会话重切一遍，会话越长模型调用越多（O(n²)）；现在已切过的不重判。

### ③ 写摘要 + 提炼（summary.py，「调用 A」）

一个事件闭合后，把它的正文发给模型，要求输出一个 JSON：

```json
{
  "title": "≤24 字，动词开头",
  "summary": "≤400 字，做了什么、结果如何",
  "experiences": [{"content": "一句话做法", "kind": "technique|pitfall|command", ...}],
  "cognitions": [{"subject": "主体", "content": "一句话事实", ...}]
}
```

提示词里写死了约束（这是质量的关键）：
- **经验**只写「换个项目也成立」的可迁移做法；一次性的输出、临时路径不写；
- **认知**只写稳定事实/偏好/约束；「今天在做 X」这种临时状态不写；
- 没把握就不写，宁可空数组不凑数。

同时，提炼前会先用事件正文去库里搜一圈**已有记忆**（`_existing_memories`），把可能重复的旧条目一起喂给模型——这样模型可以直接说「这条和 #28 重复，取代它」，而不是写完再补救。

### ④ 合并判重（consolidate.py，「调用 B」）

A 产出的是「新条目」。B 拿每条新条目 + 它的候选旧条目（按主题/线索召回最多 5 条），让模型逐条裁决：

- **new**：不重复不冲突，直接新增；
- **supersede**：新条目取代旧条目（旧条目标记 superseded，保留可查）；
- **invalidate**：新条目证明旧条目不再成立（标记 invalid，不再被召回，但正文保留可追溯）。

设计原则是「**宁可多一条重复，也不错合并丢信息**」：B 调用失败时全部按 new 落库，绝不让裁决失败阻塞记忆写入。

### 落库与索引（ingest.py `apply_summary`）

以上所有写入在**同一个事务**里完成：事件行、l3 行、FTS 全文索引、事件↔消息的绑定。任何一步失败整体回滚，不会留下「有摘要没索引」的半成品。

之后还会顺手做两件小事：
- **digest（工作记忆）**：按「最近 5 个事件 + 高重要度经验/认知/洞见」重拼一张便签，存在 `digest` 表，整个 job 结束只刷一次；
- **向量索引**（embed.py）：把新经验/认知的正文发去 embedding，结果存进 sqlite-vec 的 vec0 表。失败只降级（退回纯词法检索），不影响落库。

## 四、读取链路：记忆怎么被想起来

模型手里有 5 个工具（tools.py），由内核声明 schema、外壳注册进宿主：

| 工具 | 干什么 | 什么时候用 |
|---|---|---|
| `memory_search` | 关键词检索，返回按「相关性 × 记忆强度」排序的列表 | 用户提到「之前/上次/偏好/约定」 |
| `memory_get` | 按 id 读一条的完整内容（事件含全部正文消息） | 搜索命中后要看细节 |
| `memory_recent` | 按时间区间回放「那段时间发生了什么」 | 「昨天/上周做了什么」 |
| `memory_report` | 标记一条记忆有问题（事件→待复核；l3→invalid） | 发现记忆与事实不符 |
| `memory_self_write` | 给自己写一条自我认知 | 模型自己想记住行为准则 |

### 检索排序（retrieval.py）——三路召回 + 一次精排

**召回**（先网一批候选，宁多勿漏）：
1. **词法路**：FTS5 trigram 全文索引取 top-50（trigram 支持中文子串匹配）；
2. **语义路**：sqlite-vec 按余弦距离做 KNN（向量由 bge-m3 算出，1024 维）——「上网查」和「互联网检索」这种字面不同但意思一样的，靠它拉近；
3. **联想路**：命中条目按主线索（cues[0]）再带几条同主题的出来（上限 20 条）。

三路结果用 **RRF（倒数名次融合，k=60）** 合成一个相对名次 `rel`。

**精排**（给每个候选算一个 0–1 的分）：

```
final = 0.6 × 相关性(rel)
      + 0.4 × 记忆强度(strength)

strength = 0.45 × ACT-R激活（用得越多、越近用过，分越高）
         + 0.25 × 重要性（1–5 分归一化）
         + 0.15 × 确信度
         + 0.10 × 情境匹配（是不是本项目的）
```

再叠加三个实用机制：
- **可靠性折减**：人工标记「待复核」的事件、confidence < 0.5 的条目，强度打五折；
- **簇上限**：同一事件蒸馏出的多条经验最多出现 2 条，避免一屏全是同一件事；
- **探索位**：10% 的名额留给从未被用过的条目——不曝光就永远是冷记忆（类似「提取练习」：被召回本身会增强记忆，`use_count` +1）。

### 核心记忆注入（core.py + core-prompt.js）

除了「模型想起来去搜」，还有一条**每轮自动注入**的通道：

- 从库里挑出 `global` 且高分（importance ≥ 4/5）的洞见、经验、认知各几条，加上「设置的自我」，编译成一段 `<long_term_memory>` XML，注入**系统提示词**（预算默认 2000 字符）；
- 「自己写的自我」（memory_self_write 写的）编译成 `<self_notes>`，注入**动态上下文**；
- 注入文本带版本号（内容的 sha256 前 12 位），版本不变外壳就不更新——避免无意义地击穿系统提示词的缓存。

这就是为什么你能在这个对话开头看到 `<long_term_memory>` 里的那几条洞察——它们是上一轮维护时沉淀下来的。

## 五、洞见归纳：离线把经验熬成规律（insight.py）

经验多了之后，插件支持一次**显式的离线归纳**（设置页按钮触发，不在写入热路径上）：

1. **聚类**：两路找「同主题的经验组」——
   - 按主线索（cues[0]）分组；
   - 按向量余弦相似度 ≥ 0.65 分组（实测首线索极度分散，37 条经验散在 35 个线索上，光靠词攒不出簇，所以加了语义这一嘴）；
2. 每组（≥3 条）发给模型：「这几条经验共同支持什么通用规则？」要求至少 2 条证据；
3. 产出写入 `insight` 表，正文里保留 `source_experience_ids`——每条洞见都能回溯「凭什么」。

洞见和源经验并存，洞见不取代经验；它只是更高一层的抽象，在核心记忆注入里优先出现。

## 六、运维面：它怎么保证自己不坏

| 机制 | 在哪 | 作用 |
|---|---|---|
| 背压队列 | base.py `message_queue` | 输出队列有界（默认 1000），满了等 5 秒再丢，丢帧计数进 health，绝不卡死主循环 |
| 主线程预热 | main.py `warm_imports` | Windows 上工作线程首次 import numpy 会死锁，主线程先 import 一遍 |
| 退化链 | database.py / ann.py / embed.py | 没有 sqlite-vec → 纯词法；没有 usearch → 精确 KNN；ANN 挂了 → 退回 vec0；摘要失败 → 标记待复核不丢数据 |
| 崩溃恢复 | shell.js `createRestartPolicy` | 内核退出按退避重启；JS 侧消息投递失败放回队首重发（内核按 msg_id 幂等，重发安全） |
| 事务 | database.py | 嵌套事务自动降级为 SAVEPOINT；多步写入要么全成要么全滚 |
| 时间归一 | base.py `to_utc_iso` | 所有跨时区比较先换算 UTC；老库 +08:00 数据有一次性迁移 |
| 维护任务 | maintenance.py | 「重跑摘要」「归纳洞见」后台线程跑，进度写全局快照供界面轮询 |
| 人工管理 | admin.py | 设置页可对每张表增删查改（白名单列名、参数化 SQL、LIKE 转义），删除会同步清索引 |
| 测试 | tests/ | 570 个 Python 单元测试（transport 契约、切分、摘要、检索、并发不变量），JS 侧 node:test |

## 七、数据流总览（一张图记住）

```
你说的话
  │  （JS 外壳攒批，2.5 秒去抖）
  ▼
message 表（原文，已脱敏）
  │  ① 切分（规则 + 模型判定边界）
  ▼
event 表（一件事 + 400 字摘要）──────┐
  │  ② 调用 A：提炼                  │ ③ memory_recent
  ▼                                  │   memory_get
experience / cognition 表            │   读它
  │  ②' 调用 B：判重合并             │
  ▼                                  │
insight 表（离线归纳，≥2 条证据）─────┘
  │
  ├─→ memory_fts（词法索引，trigram）──┐
  ├─→ vec0 向量表（语义索引，bge-m3）──┤→ memory_search 三路召回
  └─→ digest（工作记忆便签）           │   精排后返回给模型
                                       │
  核心记忆（高分条目）──────────────────┘
       直接注入系统提示词（不用搜）
```

## 八、当前已知的短板（0.3.3 → 0.4.0 的方向）

最近一次真实使用验证暴露了三个相互咬合的问题：

1. **冷启动死结**：跨会话回忆只能靠关键词搜，而新会话里没有旧会话的关键词——「我之前让你做什么」这种没有主题词的问题搜不到。
2. **查到也不全**：`memory_search` 只返回 400 字摘要，细节在正文里；模型拿到摘要就答，不会自觉再调 `memory_get` 翻原文。
3. **回放有物理缺口**：`memory_recent` 只能回放**当前会话**（SQL 里 session_id 是硬过滤），「下午在另一个会话做了什么」这条路过不去。

0.4.0 已全部补上：跨会话回放（`memory_recent` 缺省跨会话）、搜索结果带 `excerpt` 命中摘录、`next_action_hint` 下一步建议、`memory_get` 分页续读、零命中时 HyDE 假想文档重试（外壳侧，复用提取槽模型）。
